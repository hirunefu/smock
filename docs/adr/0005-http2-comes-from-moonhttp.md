# HTTP/2 framing, HPACK and connection state come from moonbitstack/moonhttp

Decided by the maintainer on 2026-10-23, for spec E (HTTP/2 over h2c and TLS). smock's HTTP/2 framing, HPACK header compression and connection state (stream states, flow control, settings, field validation) come from the `http2` package of moonbitstack/moonhttp, a third-party MoonBit module on mooncakes, and not from a module of smock's own. smock keeps everything around it: the sockets and TLS, telling HTTP/2 from HTTP/1.1, mapping each stream onto the engine's request, the concurrency of streams, Faults, limits, timeouts and the denial-of-service defences. Of the packages that ship, only server imports moonhttp. The e2e tests also import, for tests only, its client-side `Conn` and its frame encoder (`http2`), its HPACK encoder and decoder (`hpack`), which the raw-frame tests build and read header blocks with, and its header field type (`header`).

The maintainer chose this over the recommended option, an own module, for what moonhttp already is. It does no I/O: its connection takes octets in and gives events and octets out, with "no sockets", which is how smock's server already drives the HTTP/1.1 codec and the OpenSSL bindings. It has no C: no `extern` declarations and no native stubs, so ADR 0001's C boundary holds, as long as moonhttp stays free of C, which a check on each upgrade keeps true. It is Apache-2.0, smock's own licence. And its HPACK tests use the test vectors of RFC 7541 Appendix C. It covers all ten frame types of RFC 9113, the preface, the stream states, flow control, settings, the field rules of RFC 9113 §8.2, the presence, order and uniqueness of pseudo-header fields (§8.3), and limits on the header list and on concurrent streams. smock checks the values of `:path` and `:authority` itself. So smock does not write and maintain several thousand lines of protocol code before HTTP/2 can ship.

## Considered Options

- **An own module, `smock/http2`, as ADR 0001 and #1's story 80 planned (the recommended option).** Full control of the code, a module smock could publish, and nothing new for the no-I/O check, which lets a protocol module import only MoonBit's core. Not chosen: HPACK, Huffman coding, framing, stream states and flow control would all be smock's to write, test and keep up with, ahead of HTTP/2 and then gRPC.
- **A copy of moonhttp's packages kept in this repository.** Control without writing the code. Not chosen now: smock would maintain the copy, and the copy would bring moonhttp's own dependency (moonvar) with it. It stays the way out if moonhttp stops being maintained or diverges from what smock needs.
- **nghttp2 through C.** Already rejected by ADR 0001.
- **Other MoonBit modules.** One HTTP/2 module on mooncakes carries its own OpenSSL C code, against ADR 0001. moonbitstack/moonrpc is a gRPC server that drives its own sockets and builds its HTTP/2 on moonhttp; it bears on gRPC (spec F), not on where HTTP/2's framing comes from.

## Consequences

- **ADR 0001 holds, with one statement narrowed.** smock is still MoonBit with C only for TLS, and HTTP/2 is still MoonBit, independent of I/O and free of C. What changes is ADR 0001's "HTTP/1.1, HTTP/2, gRPC framing and WebSocket are ours to build and maintain": HTTP/2's framing, HPACK and connection state are now a third party's. ADR 0001 gains a follow-up, published with this ADR, that points here. #1's plan to make HTTP/2 a separate smock module, to publish on mooncakes, is dropped. This ADR decides HTTP/2 only; gRPC and WebSocket decide their own.
- **The no-I/O rule is unchanged.** The packages that decide a response (Definitions, the engine, templates and the others the no-I/O check lists) never import moonhttp, so the no-I/O check and the wasm-gc build stay as they are. If a later design wants HTTP/2 or HPACK code in a no-I/O package, that needs a new decision, because the check forbids it. The C check covered smock's own files only; spec E widens it to scan the resolved dependencies in CI, so it keeps moonhttp and its modules free of C (below).
- **Costs and risks.**
  - **Third-party code on the request path.** A bug in moonhttp is a bug in smock, and smock cannot fix it on its own schedule.
  - **Young and fast-moving.** Its first version, 0.1.0, came out on 2026-09-21; 0.14.0, the sixteenth, on 2026-10-22. Its API and behaviour can change between minor versions, and MoonBit itself changes monthly (ADR 0001).
  - **Transitive modules.** moonhttp imports moonvar, moondate, mooncrypt and moonbase (as of 0.14.0). They are more code from the same third party, and NOTICE and the SBOM must name them.
  - **Not yet measured.** Its CPU and memory cost under smock's load, its behaviour against h2spec and other HTTP/2 implementations, and whether it builds with smock's pinned toolchain had not been checked when this was decided. Its own tests are its only conformance evidence so far. Reading its code since shows that two h2spec cases (http2/5.1.1/2 and http2/5.1/12) fail, because moonhttp answers a used stream ID with a stream error, not a connection error. smock turns it into a connection error (spec E), and the gap is reported upstream.
  - **Defences are not all there.** moonhttp bounds the header list and the concurrent streams, but counting Rapid Reset, MadeYouReset and frame floods is left to its user. As of 0.14.0 it also sizes its HPACK encoding table from the client's setting with no cap, gives no event for the streams it refuses, and does not bound the octets it queues. It also answers a header list over its bound with a stream reset, not 431. smock caps the table by lowering the client's setting, counts refused streams from the frames it hands over one at a time, reads no more while output is unwritten, and gives moonhttp a header-list bound twice its own limit so that it can answer 431 itself.
- **How they are contained.**
  - **An exact pin.** smock imports moonhttp at one exact version. moon treats the version as a minimum, so any change that raises the version moonhttp resolves to, including a new or upgraded module that needs a later moonhttp, is an upgrade and goes through the same gate. A CI check fails when the resolved version differs from the one named; that check is what makes the pin exact.
  - **Deliberate upgrades.** A new version is taken on purpose, on an integration branch, and merged only after h2spec, smock's e2e tests, the check by hand with other clients (below) and the pre-merge local and GKE benchmark runs, compared with the previous runs. The C check's scan of the resolved dependencies keeps moonhttp and the modules it imports free of C source, `extern "C"`, native stubs and link flags. The weekly build against the latest MoonBit toolchain shows a toolchain break early.
  - **Tests from outside.** h2spec, pinned, runs in CI against both traffic ports. It shares no code with moonhttp, so it is the standing guard against moonhttp's client and server sharing one mistake. It checks RFC 7540 and RFC 7541. e2e tests drive smock over real sockets, the known denial-of-service patterns included, and cover RFC 9113's additions to the field rules, which h2spec does not test. They check the limits and rules moonhttp enforces as well as smock's own, so an upgrade that drops one fails them. A check by hand with curl, Go, a JVM client and a browser runs before spec E's merge and on every moonhttp upgrade.
  - **One place to change.** Of the packages that ship, moonhttp is used only in the server package, behind smock's own mapping onto the engine. Replacing it, with a copy or with an own module, would touch that package and no engine code. It would also mean a new HTTP/2 client, frame encoder and HPACK coder for the e2e tests, the denial-of-service tests included.
  - **Measured where it runs.** The h2c and h2-over-TLS benchmark cases are held to the same targets as HTTP/1.1, the memory targets included.
