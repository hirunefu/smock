# The boundary ledger

This is the third of the [four ledgers](../../CONTRIBUTING.md#the-four-ledgers)
that judge smock's tests. Every limit that a spec or smock's documents state
is tested at the limit and just past it, with the smallest input that
crosses it. A limit in the code that no document states is a finding: once
the maintainer confirms it, the documents state it, and it is tested like
the others. Each row below is one limit, or one range with its two ends. It
cites where the limit comes from, names the packages that hold it, and
names the tests on each side of it, or the ticket that adds what is
missing. The [use-case ledger](use-cases.md) does the same for features and
messages.

[Keeping the ledgers current](../../CONTRIBUTING.md#keeping-the-ledgers-current)
in CONTRIBUTING says how each change keeps them up to date.
`scripts/check-ledgers.py` checks every row on every push, as it checks
the use-case ledger.

For a range, "at the limit" names the tests that accept its ends, and
"just past it" those that refuse the value past each end. Where a test
holds both sides, it is named in both columns. A test that a row names is
the only test of that row for the
[removal rule](../../CONTRIBUTING.md#removing-a-test).

## Baseline

A survey of the documents at d953f320 tabled the 40 most important limits.
Each was checked again on the tip of the test review's integration branch,
be2b8e0b, against the code and the tests there. Where a survey row held
several limits, they are split here into rows with the same number and a
letter (L15a, L15b, ...). Rows L41 to L43 are limits that the test review's
spec names beside the survey's 40.

| | At d953f320 | At be2b8e0b |
|---|---|---|
| The survey's 40 rows | about 33 tested on both sides, as the survey counted; 32, rechecked | 34 tested on both sides, 6 partly |
| The 68 rows of this ledger | | 56 tested, 11 partly, 1 open |

A survey row counts as tested on both sides only when every row split from
it is. The recheck at d953f320 differs from the survey's own marks in which
rows it counts: see below.

The survey's 40 limits were not every limit the documents state. #375
listed the rest: rows L44 to L92, 69 rows split by letter where one
sentence states several limits, each found by
[the search for documented limits](#the-search-for-documented-limits) and

## The search for documented limits

#375 searched smock's documents for the limits they state, so that each
package's L4 ticket finds its limits in this ledger. Anyone can run the
search again, and read each line it finds that no row cites.

**What it reads.**

- The user documents: README.md, GLOSSARY.md, SECURITY.md, the Helm
  chart's [README](../../charts/smock/README.md), and the documents under
  `docs/` that [docs/README.md](../README.md) lists before "Contributing
  to smock". CHANGELOG.md is left out: it records changes, and each limit
  it names that still holds is stated in one of the others.
- The help texts: the `about` strings of the commands and their settings,
  in `settings/settings.mbt` and `cmd/smock/main.mbt`. The running guide's
  [settings table](../running.md#settings), which repeats them, was read
  row by row too.
- The modules' own documentation: the READMEs of `grpc`, `protobuf`,
  `re2` and `xml`, and the doc comments of `http1` and `yaml`, which have
  no README.
- The [JSON Schema](../../schema/v1/definitions.json) of Definition files
  and the Admin API's [OpenAPI document](../../openapi/admin.json), by
  their keywords for bounds.

**The commands**, run from the root of a checkout:

```sh
docs=$(git ls-files README.md GLOSSARY.md SECURITY.md charts/smock/README.md 'docs/*.md' |
  grep -v -E '^docs/(ledgers|adr|agents)/|^docs/(README|merging-into-main|releasing)\.md$')
words='\bmost\b|\bleast\b|\bthan\b|\bup to\b|\bup$|limit|bound|maxim|minim|longest|largest|smallest|shortest|[KMG]iB\b|deep|depth|[0-9]`? to\b|\bto `?-?[0-9]|\b(pass(es)?|past|above|below|over|under|beyond|exceeds?|within)( the| its)? `?-?[0-9]|\b[0-9][0-9,]* (bytes|octets|characters|code units|entries|streams|frames|levels|values|digits|seconds|ms|days|iterations|instructions|writes|documents|names|files|responses|times)\b'
git grep -n -i -E "$words" -- $docs
git grep -n -i -E "$words" -- grpc/README.mbt.md protobuf/README.mbt.md re2/README.mbt.md xml/README.mbt.md
git grep -n -E '^\s*///' -- 'http1/*.mbt' 'yaml/*.mbt' ':!*_test.mbt' ':!*_wbtest.mbt' | grep -i -E "$words"
git grep -n -E '\babout[=:] *"' -- settings cmd/smock ':!*_test.mbt' ':!*_wbtest.mbt' | grep -i -E "$words"
git grep -n -E '"(minimum|maximum|exclusiveMinimum|exclusiveMaximum|minLength|maxLength|minItems|maxItems|minProperties|maxProperties)"' -- schema/v1/definitions.json openapi/admin.json
```

The words are those of a limit ("at most", "at least", "more than", "from
1 to 100", "up to", "limit", "over 8 KiB", "256 deep"), and a number with
a unit. A phrase split over two lines is still found by one of its single
words, such as `most`, `least` or `than`, or by the number next to `to`.

On 5bf509f1 the commands give 951 lines in the 40 user documents, 85 in
the four READMEs, 63 in the doc comments, 11 in the help texts and 86
keywords in the Schema and the OpenAPI document: 1,196 hits. Each was read
in its paragraph.

**What counts as a limit.** A number that the documents give for what
smock accepts, keeps, writes or waits for, where a value at the number is
taken one way and the value just past it another: a size, a count, a
depth, the range of a field, a setting or an argument, a range of
characters, or a time after which smock acts. These hits state no limit,
and got no row:

- Measurements and estimates: the benchmarks' rates and latencies, the
  memory a call or a set costs, and any figure given as "about".
- Limits of other software that the documents only describe: Mockoon's,
  the SDKs' retries, Kubernetes' ConfigMaps, GKE Autopilot's ratios, the
  Helm chart's resources, and how long CI keeps an artifact.
- A setting's default alone, such as a port, and values in examples, such
  as `--body-limit 32`.
- Rules of one: at most one Mock marked `default`, one `Range` field, one
  colon in an XML name, exactly one message in a unary call, exactly one
  of `response` and `responses`. So are "non-empty" (`minLength` 1) and
  "at least one" alone. The use-case ledger's features cover them.
- Conditions on a count, such as an `after` above 0, `evicted` above 0 or
  more than one replica. The use-case ledger's features cover them.
- The forms of what smock writes: ids of 24 characters, the ranges of the
  date tokens, the buckets of a metric, the 2^31-1 that the drain's first
  GOAWAY names, the fields of the Admin API's replies, and the fraction
  digits a Timestamp prints.
- The parts of a bound's count that a row already holds: what a Journal
  entry (L12, L13), a Variable or a copy (L14), a header field (L04) or a
  message's octet (L28a) counts.
- That a number keeps its digits beyond 2^53: no limit, but the absence of
  one.
- moonhttp's 32-bit count of a decoded header list, which wraps past 2^31
  octets: smock's own count still refuses such a list with 431, which is
  L04.

Every other hit states a limit. Each limit is cited by its row: the
survey's rows, with L41 to L43, or a row that #375 added.

**Limits in the code that no document states** are findings, not rows:
#375 takes each one that checking the rows' packages met to the
maintainer. Checking them met one: `http1`'s parser takes a negative body
limit as 0, so a request with a body of one byte gets 413.
`Parser::Parser`'s documentation said nothing of a negative limit. The
maintainer confirmed it on 2026-11-17, the documentation now states it,
and it is row L93.

## Gaps that no ticket closes

A gap that no ticket of the test review closes is filed as an issue, which
its row names. Until it has its number, its row names the ticket that files
it.

- **G4, closed by #376.** No test took an `after` of 2^53 - 1, the
  largest that the Admin API's OpenAPI document allows, in the unmatched
  list's query string, which `server` reads (L15b). The paging test of the
  unmatched list now takes it. #333 tests the Journal query's body, which
  `engine` reads, as a limit of this ledger in `engine`.
- **G5, closed by #383.** Four limits that `server` holds had no test on
  one side, and no ticket takes `server` to L4: the 100 PING passes that
  smock saves up (L49), a Variable name of 128 characters through the
  Admin API (L56), a reply's metadata block that takes the client's
  SETTINGS_MAX_HEADER_LIST_SIZE exactly (L72), and the response index 99
  through the Admin render operation (L83a). e2e tests now take each
  missing side, the last through `smock render --response` too.
